Phase 16.7.8 step 7v — lxml consumer court: push blocker fixed, schematron
crash fixed, and the remaining suite failures measured against a baseline.

WHY THIS RECEIPT EXISTS
-----------------------
The step-7v option flip makes lxml's default parse-option set
(NOENT | NOCDATA | NONET | COMPACT | BIG_LINES) eligible for the persistent
push driver. Before it every lxml parse stayed on the O(N^2) replay engine and
lxml's 2.2 GB test_very_large_sourceline_iterparse hung for more than 240 s.
After it the suite runs past that test (20.5 s in the debug build the court
uses; ~2.4 GB/s in release) and can finally be measured end to end.

PART 1 — A REAL BUG FOUND BY THE UNBLOCKED SUITE (FIXED)
-------------------------------------------------------
The suite aborted rc=139 at the `lxml.etree.Schematron` doctest:
`xmlSchematronNewValidCtxt` cloned a `CompiledExpr` from freed memory.

Root cause: `xmlSchematronParse` returned its PARSER CONTEXT as the schema
pointer. Upstream keeps `_xmlSchematronParserCtxt` and `_xmlSchematron` as two
objects; lxml does

    self._c_schema = xmlSchematronParse(parser_ctxt)
    finally: xmlSchematronFreeParserCtxt(parser_ctxt)

and frees the schema only at dealloc, so the schema pointer was dangling
(and `xmllint --schematron` double-freed). Fix: a distinct
`SchematronParserCtxt` type and a NEW `Box<SchematronSchema>` from
`xmlSchematronParse`; `xmlSchematronFreeParserCtxt` frees only the parser
context.

Verified against the oracle with a direct probe (no lxml):

    candidate  validate -> False   rc=0
    oracle     validate -> False   rc=0

New regression tests: `parser_ctxt_and_schema_are_distinct_allocations`,
`parse_twice_recompiles_independently`; the existing C-ABI lifecycle tests were
corrected to the upstream sequence.

ROOT CAUSE FOUND FOR THE LARGEST SINGLE CLUSTER (isoschematron, 21 + a doctest)
------------------------------------------------------------------------------
`iso_dsdl_include.xsl` compiles, but its generic `node()` copy template never
runs: the process outputs only the two `DSDL_INCLUDE_*` PIs. Bisection (drop one
specific template at a time) isolates it to this template:

    <xslt:template match="*[@xlink:href][not(parent::*[@xlink:type='complex'])]
        [not(@xlink:type) or (@xlink:type='simple')][@xlink:show='embed']
        [not(@xlink:actuate) or (@xlink:actuate='onLoad')]" mode="dsdl:go">

With that template removed the transform copies the schema correctly
(outlen 403, root=schema) — the candidate then matches the oracle. With it
present the generic `node()` template (priority -1) is shadowed and the XLink
body runs for the schema root, emitting the PIs. This is an XSLT match-PATTERN
compilation defect (predicates on a wildcard step are apparently not applied),
not a push-parser issue; a minimal `mode`/prefix repro does NOT reproduce it, so
it is specifically the multi-predicate wildcard match.
